# GNOME provider native-display bootstrap

The installed Ubuntu GNOME portal backend requires Mutter's `org.gnome.Mutter.ServiceChannel` interface before it creates a native GTK display. Its `OpenWaylandServiceConnection` method takes portal service type `1` and returns a Unix file descriptor (`(u) -> h`). The backend opens this connection before acquiring its well-known portal bus name. GNOME 51 also requests typed connections for Nautilus as the file chooser (type `2`) and the control-center global-shortcuts helper (type `3`).

The genuine GTK run for capture PR #252 at `e4bea38e2a2522e3555a24a285bbf81b180f6a14` failed `G-PORTAL-CONSENT` on 2026-10-04. The installed backend logged “Non-compatible display server, exposing settings only”; the frontend reported a missing ScreenCast interface and returned CreateSession response 2. This occurred before a picker existed. The same run passed native no-XWayland startup, server/XIM restart, long-folder viewport and held edge paging, native IBus composition/candidates, and genuine GTK3 XIM.

Roost provides the requested ordinary Wayland connection only to a same-user D-Bus caller whose PID resolves to the installed, root-owned, non-writable executable for the requested type. Type `1` accepts the GNOME portal backend, type `2` accepts `/usr/bin/nautilus`, and type `3` accepts `gnome-control-center-global-shortcuts-provider` in `/usr/libexec` or `/usr/lib`. A binary admitted for one type is not admitted for another. This bootstrap cannot require the portal's not-yet-acquired well-known name. Connections use ordinary client permissions, not the IME bridge or shell role. Typed providers retain one live typed connection per unique caller. Ordinary clients may open multiple displays; both methods share a maximum of 32 live connections, and disconnected connections free their slots. Unsupported service types are rejected.

Opening a display is not capture admission. The existing ScreenCast methods still require the current unique portal owner or supervised shell, enforce session ownership, and deny or revoke capture while locked. A backend may initialize its ordinary display while locked, just as ordinary Wayland clients may connect, without gaining a capture grant.

The real security client checks denial for all three types from an untrusted caller, including forged portal, Nautilus and global-shortcuts-provider service names. The full current-head GNOME picker Cancel/Share, frame consumption, owner Close, lock and disconnect proofs remain required before acceptance.

Upstream contracts: [Mutter 46 ServiceChannel](https://raw.githubusercontent.com/GNOME/mutter/46.0/data/dbus-interfaces/org.gnome.Mutter.ServiceChannel.xml), [GNOME portal 46 native display initialization](https://raw.githubusercontent.com/GNOME/xdg-desktop-portal-gnome/46.0/src/externalwindow-wayland.c).

The subsequent Ubuntu GTK run at `eb572636` reached the real ScreenCast interface and returned CreateSession response 0, confirming native bootstrap. SelectSources then failed with “Unavailable cursor mode 1”. The proof had launched the backend and frontend together; GNOME 46 publishes ScreenCast capabilities asynchronously, while the frontend snapshots those properties on initialization. The driver now waits for actual backend properties before launching the frontend, then requires frontend properties too: version at least 2, monitor source support and hidden-cursor support. Each call has a 500 ms timeout and the overall wait is bounded to 30 seconds, without D-Bus auto-start. The original cursor request and picker/security assertions stay unchanged.

The corrected ordering passed the actual GNOME 51 reference journey with the retained `eb572636` compositor and shell binaries on 2026-10-04: Cancel, Share, frame consumption, Close, client/backend disconnect, active-stream lock revocation and locked denial. Backend and frontend readiness evidence both recorded version 5, source types 7 and cursor modes 7. This separate control does not replace the pending full current-head Ubuntu GTK and package checks.

## Ordinary options-based display connections

`OpenWaylandConnection(a{sv}) -> h` accepts an authenticated same-user process with ordinary Wayland client permissions. It is available while locked, as ordinary display connections are, and does not confer a trusted provider, capture, virtual-keyboard or session-lock role. Its optional string `window-tag` becomes window metadata for this connection; an explicit xdg-toplevel tag overrides it, and other clients inherit no tag. Unknown options and incorrectly typed tags are ignored as in Mutter 51. Tags exceeding 1024 UTF-8 bytes are rejected with InvalidArgs to bound retained metadata.

The options and typed methods share the live connection budget, while an ordinary connection does not consume the caller's single typed-provider slot. The real untrusted D-Bus proof opens two tagged ordinary connections, completes actual `wl_display.sync` on both, then still requires typed-provider and capture denial from that same caller. The existing GTK and GNOME 51 portal reference drivers run this proof both unlocked and locked. Unit coverage separately drives socket sync, exhaustion, disconnect slot reuse, real xdg windows, inherited tags and explicit tag overrides. Execution results must be retained from the current head before qualification; this description does not claim a passing end-to-end Nautilus Open/Save journey.

## Standalone running applications

GNOME's running-app list requires at least one window without a transient parent. Roost snapshots that eligibility from actual Wayland role relationships (including imported foreign parents) or managed X11 parent metadata, rather than treating a supplied application ID as evidence of a standalone window. A transient dialog's focus still counts for its application when that application also has a standalone window; inactive applications omit `active-on-seats`, matching GNOME 51. Window selection itself continues to include dialogs.

Candidate regression coverage drives real same-client parent assignment/detachment and cross-client export/import/withdrawal, then checks the window manager's eligibility and removal. App-list tests cover transient-only providers, focused dialogs belonging to standalone apps and detached dialogs. Current-head execution and admitted portal/shipped-image qualification remain required. Authenticated sandbox identity, actual auxiliary-X11 type transitions through an admitted portal and full GNOME app selection in #410 remain unqualified.


## Eligible windows in the GNOME picker

`GetWindows` filters the shared snapshot using live window-role metadata. Native xdg toplevels (including transient dialogs and foreign-parented file pickers) remain eligible. Managed X11 windows with Normal, Dialog or Utility types remain eligible; a missing type defaults to Normal. X11 desktop, dock, combo, drag-and-drop, notification, menu, popup/dropdown menu, splash, toolbar and tooltip types are excluded. The pinned Smithay patch recognizes all fourteen EWMH window types, including four auxiliary types it previously treated as unrecognized. Override-redirect windows are already refused by the XWM map path and the picker eligibility check also rejects them. Modal X11 dialogs retain the Dialog type. Property changes are read for each publication, so an eligibility change updates the snapshot and emits `WindowsChanged`.

This window filter is independent of `GetRunningApplications`: the app list still uses standalone-window relationships and includes focus from all of an eligible app's windows. Neither client-supplied window types nor this enumeration grant capture/provider authority. Tests cover the GNOME type matrix, independent app-focus aggregation, real native transient/foreign-parent relationships and unmapping. The GTK proof changes all fourteen real EWMH types on its mapped X11 client, retains each compositor policy result and restores the absent-type default; execution of this new proof is pending. Admitted-portal X11 type-change selection, sandbox IDs and shipped-image VM qualification remain required; this source change does not close #410.

## Original service-client process identity

A service channel creates its socketpair inside Roost, so ordinary socket peer credentials can describe the compositor rather than the requesting application. Admission now obtains UID, PID and optional process descriptor together through the bus's `GetConnectionCredentials` and retains that original credential snapshot on the inserted Wayland client. The same-user, installed-provider and connection-budget checks remain separate from capture and input authorization.

The compositor's `authenticated_service_client_pid` API returns a numeric PID only while a bus-supplied `ProcessFD` pins a live original process. A missing descriptor, an exited process or a polling error yields no identity; it never substitutes the socketpair creator or opens a new descriptor from a potentially recycled PID. Older buses that omit `ProcessFD` can still open their ordinary display connections. The local ordinary-user bus probe returned UID/PID but no process descriptor; descriptor support in the shipping GNOME session must be checked separately.

This is groundwork for #410, not sandbox metadata publication. Directly accepted native clients, X11 identities, Flatpak/Snap identities, actual portal selection and shipped-image qualification remain required. The new tests use actual child-process descriptors and a real Wayland surface to check original identity, socketpair-creator differences and peer exit; they are awaiting CI execution. Primary contract: [D-Bus GetConnectionCredentials](https://dbus.freedesktop.org/doc/dbus-specification.html#bus-messages-get-connection-credentials).

The native-client follow-up captures `SO_PEERCRED` and `SO_PEERPIDFD` from the accepted Wayland socket before inserting it. The latter pins the original connecting process through the kernel's stored peer reference, rather than looking up its numeric PID later. `authenticated_client_pid` reads either that original native identity or the original service-channel snapshot; its service-only companion still rejects native connections. Unsupported socket options and missing credentials leave identity unknown while permitting the ordinary display connection. These records confer no IME, provider, capture or input role.

Native tests connect a genuinely separate child process to a Unix listener and require its pinned identity to expire on exit. A socketpair test separately requires ordinary client state without an IME or service role. This follow-up is awaiting Rust/GTK/native VM execution and shipping-kernel qualification. It does not publish sandbox identities or implement X11 process attribution. Kernel contract: [Linux 6.5 SO_PEERPIDFD implementation](https://github.com/torvalds/linux/blob/v6.5/net/core/sock.c).

## Introspect desktop dimensions

`org.gnome.Shell.Introspect.ScreenSize` follows the bounding logical desktop layout rather than selecting the primary monitor. The compositor publishes the same logical output inventory used for placement, translating negative origins for the size calculation and including gaps; mirrored output geometry is counted once. Empty output layouts return zero dimensions, and calculations use wider intermediates with the D-Bus signed-integer limit. Initial reads use the current layout even before the service thread starts.

The runtime emits standard `PropertiesChanged` notifications only when the effective dimensions change. The candidate graphical `G-INTROSPECT-SIZE` journey subscribes a real Gio client before GNOME `ApplyMonitorsConfig`, then checks initial property reads and the actual fractional-scale/restoration notifications. Headless compositor-state regressions separately cover negative origins, primary changes, logical resizing, mirrored layouts, translations, disconnects and coordinate extremes. Current-head execution must pass before qualification; this does not establish shipped-image multiple-output, rotation or physical hotplug acceptance in #411/#342.


### Transient application association

A transient dialog belongs to its ultimate mapped parent application, including a picker from a separate provider process. The manager follows actual native/foreign parent relationships or mapped X11 transient XIDs. Cycles fall back to the original window and unknown/unmapped parents are not followed. Runtime snapshots retain the dialog's raw application ID/X11 class separately from the inherited application identity; `GetWindows.app-id` and running-app focus use the inherited identity. A focused Nautilus picker for Text Editor therefore contributes focus to Text Editor while its raw client metadata remains Nautilus. Withdrawing its imported parent restores the picker's own application identity. Anonymous applications share the ultimate parent's stable window identity.

This metadata association grants no input, capture or provider role. The new regression drives genuinely different parent/dialog/provider app IDs through real Wayland parent assignment, foreign import/withdrawal and unmapping; map tests verify app focus and preserved X11 class. These regressions executed successfully at candidate `aabb55e`; the integrated main-based source must pass its own CI gates. ## Trusted Wayland dialogs for X11 parents

Candidate source implements the pinned libgxdp `mutter_x11_interop` version 1 contract. Only connections admitted through the authenticated typed service method can see/bind it; ordinary native, ordinary options-based service and IME connections do not gain this capability. This is separate from provider/capture/input permission. Owned live xdg surfaces can request an existing managed X11 parent while unlocked. Invalid or destroyed parents are ignored, and deferred requests retain the original managed window generation rather than resolving a reusable XID later.

The unified parent lookup is used by placement, stacking, modal focus, standalone eligibility and inherited application identity. A dialog shares its parent's workspace and centers over it after the initial buffer determines its size. Parent unmap clears the association; closing a focused dialog returns focus to the surviving parent. Managed parents need not already have an associated Wayland buffer. Preferred scale follows the placed dialog geometry.

A registry regression distinguishes typed service admission from ordinary service liveness and native clients. The reference image adds rootless Xwayland and repeats real Nautilus Open/Save cancel/accept with an actual GTK X11 caller: it retains the XID and managed parent identity, requires centered placement, dialog focus and inherited app association, and requires focus returning to the still-live parent.
