# Installed-backend Screenshot consent

Tuna Desktop uses the installed GNOME 51 Screenshot backend and the installed GTK Access backend. The shipping portal preference explicitly selects `Access=gtk`: GNOME's Access backend delegates its consent dialog to GNOME Shell's Access interface, which Tuna Desktop does not provide. With the old preference, the real frontend returned response 2 before a dialog could appear. GTK supplies this UI-only dialog; it gains no compositor capture authority.

The reference journey requires a real Deny, no screenshot URI, then a real Allow and a readable 1280×800 PNG with varied desktop pixels. There is no frontend result before the decision. The isolated PermissionStore remembers Deny for the host fixture's empty app ID. The driver records that `no` permission, removes only that fixture permission through the real API, and verifies its removal before a fresh Allow journey. Production permission state is untouched.

Locked Screenshot and ScreenshotWindow calls first authenticate the original trusted desktop identity. Unauthorized callers retain AccessDenied. An authenticated caller receives the documented `(success=false, filename="")` result while locked, without entering frame capture. Frame delivery still rechecks lock; a lock arriving after admission or another normal capture failure returns the same tuple. ScreenCast and RemoteDesktop admission and revocation rules are unchanged.

GNOME 51's Screenshot backend ignores the false success flag and completes its frontend request with response 0 and an empty URI. The proof records this upstream translation; it requires no usable URI and no new or changed screenshot file. Previously an AccessDenied error correctly prevented capture, but the backend printed it without completing the frontend request. An isolated documented-false-result contract probe confirmed the completion path; that fixture is not compositor acceptance. The real packaged producer passed this completion path in [CI 37214394538](https://github.com/tuna-os/tuna-desktop/actions/runs/37214394538); candidate `3249f362` combines exact head `5e19b47` with main `153ee8f`. All sixteen current-head checks passed, including GTK, package, DRM, VM and the final ledger.

The retained pre-change actual producer control passed Deny and Allow with a real image, then failed the locked request deadline. Its backend log reported `AccessDenied: session locked` and no new image was captured. The accepted GNOME 51 run passed Deny/no URI, fresh Allow/readable varied 1280×800 PNG, and locked response 0 with an empty URI; saved-image hashes remained unchanged. The same package passed complete ScreenCast and Remote/EIS consent and revocation journeys. Interactive screenshot customization, area selection through the external portal and color picking remain unimplemented; this proof covers the noninteractive Screenshot request and its permission lifecycle.

Upstream contracts: [GNOME 51 Screenshot backend](https://raw.githubusercontent.com/GNOME/xdg-desktop-portal-gnome/51.0/src/screenshot.c), [its screenshot dialog callback](https://raw.githubusercontent.com/GNOME/xdg-desktop-portal-gnome/51.0/src/screenshotdialog.c), [frontend permission handling](https://raw.githubusercontent.com/flatpak/xdg-desktop-portal/1.20.3/src/screenshot.c), [PermissionStore API](https://raw.githubusercontent.com/flatpak/xdg-desktop-portal/1.20.3/data/org.freedesktop.impl.portal.PermissionStore.xml).
